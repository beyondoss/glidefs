# Pack Size Analysis

**Date**: 2026-02-19
**Default**: `DEFAULT_BLOCKS_PER_PACK = 500` (configurable per-export)
**Block size**: 128KB (fixed; see `BLOCK_SIZE_ANALYSIS.md`)

## Method

All measurements use real filesystem data from 5 forked ext4 disk images (512MB
each, generated by `scripts/gen_dedup_images.sh`). The forked set simulates the
production pattern: a blessed Ubuntu 22.04 + Node 20 base image, copied, then
each fork runs `npm install` for different packages.

**Performance tool**: `cargo run --release --bin pack_size_measure`

15,872 non-zero 128KB blocks were read from the images (1,984MB of real
filesystem content). Each pack size was tested by splitting these blocks into
packs of that size, assembling the pack (blake3 hash + LZ4 compress + pack
wire format), then measuring decompress/extract on the assembled pack bytes.

Timings are medians of 10 iterations with 2 warmup iterations, measured on
the same machine at release optimization level.

**Churn tool**: `cargo run --release --bin block_churn_measure`

Compares base and forked images block-by-block (BLAKE3 hash of each 128KB
position) to measure how many blocks actually change per workload. Reports
spatial clustering and pack simulation.

## Measured Block Churn

### Forked images (production pattern)

Each fork starts from the same blessed base image (Ubuntu 22.04 + Node 20),
then runs a workload. This is the GlideFS production pattern: fork → write → flush.

| Workload | Dirty Blocks | Data | Packs at 500 |
|----------|-------------|------|--------------|
| `npm install express` | 50 (1.2%) | 6.2MB | 1 |
| `npm install express` #2 | 51 (1.2%) | 6.4MB | 1 |
| `npm install next react` | 1,071 (26.1%) | 134MB | 3 |
| Express + 50 app files | 61 (1.5%) | 7.6MB | 1 |
| `git clone --depth 1` express | 34 (0.8%) | 4.2MB | 1 |
| `pip3 install django` | 9 (0.2%) | 1.1MB | 1 |
| 10,000 small files | 391 (9.5%) | 48.9MB | 1 |
| npm + git + 150 source files | 111 (2.7%) | 13.9MB | 1 |

Cross-filesystem comparison (npm install express):

| Filesystem | Dirty Blocks |
|------------|-------------|
| ext4 | 50 |
| XFS | 73 |
| btrfs | 54 |

Filesystem choice has minimal impact. XFS is slightly higher (more metadata
blocks changed), same order of magnitude.

At `DEFAULT_BLOCKS_PER_PACK = 500`: **7 of 8 workloads produce 1 pack.** The
heaviest (Next.js) produces 3 packs. Every fork from a blessed base fits in
1-3 S3 PUTs regardless of pack size.

### Independent images (no shared base — worst case)

Same workloads, but each image is built from scratch (no fork). This is what
happens without `bless`.

| Fork | Dirty Blocks | % of Image |
|------|-------------|------------|
| Express | 3,061 (383MB) | 74.7% |
| Express #2 | 3,058 (382MB) | 74.6% |
| Next.js | 3,927 (491MB) | 95.9% |
| App | 3,070 (384MB) | 74.9% |

**Forking from a blessed base reduces churn by 50-60x.** This is the `bless`
value proposition in hard numbers: 50 dirty blocks vs 3,061.

### Spatial clustering

Dirty blocks are not randomly scattered. They cluster in contiguous runs,
which means they land in the same packs and die together (good for GC).

**Forked (ext4) — % of dirty blocks in contiguous runs:**

| Run Length | Express | Next.js | 10K Files | Mixed |
|------------|---------|---------|-----------|-------|
| 1 (isolated) | 10.0% | 0.7% | 1.0% | 9.0% |
| 2-4 | 10.0% | 0.6% | — | 1.8% |
| 5-16 | 24.0% | 5.8% | 4.1% | 16.2% |
| 17-64 | 56.0% | 23.0% | 17.6% | 73.0% |
| 65+ | — | 69.9% | 77.2% | — |

Pip install (9 blocks) is 78% isolated — too few blocks for meaningful runs.
Git clone (34 blocks) is 47% in runs of 5-16.

**Independent (ext4):**

| Run Length | Express | Next.js |
|------------|---------|---------|
| 65+ | 98.7% | 97.2% |

Forked workloads: 56-95% of dirty blocks in runs of 5+.
Independent workloads: 97-99% in runs of 65+ (sequential install layout).

This validates the GC assumption: blocks written together during a deploy
tend to die together at the next deploy. Packs have cohort-correlated
lifetimes.

## Compression

LZ4 compression ratio on real filesystem blocks: **1.93x** (128KB raw -> ~66KB
compressed, averaged across all 15,872 blocks).

Consistent across all pack sizes — compression operates per-block. Index
overhead (pack header + 24-byte entries per block) is negligible: 0.04%.

## S3 Transfer Model

Conservative same-region estimates: 20ms fixed latency + 100 MB/s per
connection.

| Blocks/Pack | Avg Pack Size | S3 Transfer | S3 GET Total | Amortized/Block |
|-------------|--------------|-------------|-------------|-----------------|
| 10 | 665KB | 6.5ms | 26.5ms | 2.65ms |
| 25 | 1.6MB | 16.2ms | 36.2ms | 1.45ms |
| 50 | 3.2MB | 32.4ms | 52.4ms | 1.05ms |
| 100 | 6.5MB | 64.6ms | 84.6ms | 0.85ms |
| 200 | 12.9MB | 129.3ms | 149.3ms | 0.75ms |
| **500** | **31.9MB** | **319.0ms** | **339.0ms** | **0.68ms** |
| 1000 | 63.2MB | 631.7ms | 651.7ms | 0.65ms |

The amortized S3 cost per block follows a 1/N curve with a fixed offset.
The knee is around 100 blocks:

- 25 -> 100: saves 0.60ms/block (41% reduction)
- 100 -> 200: saves 0.10ms/block (12%)
- 200 -> 1000: saves 0.10ms/block (13%)

Beyond 100, diminishing returns on amortized GET cost.

## Cold Read Latency

Two paths for cache misses:

1. **Range-read** (`resolve_chunk`): S3 range request for one block's
   compressed bytes. ~20ms fixed + tiny transfer. Pack size irrelevant.

2. **Prefetch** (`resolve_pack`): GET entire pack, decompress all blocks
   into clean cache.

| Blocks/Pack | S3 Download | Decompress | Total | Blocks Cached |
|-------------|-------------|------------|-------|---------------|
| 25 | 36.2ms | 1.0ms | ~37ms | 25 |
| 100 | 84.6ms | 4.4ms | ~89ms | 100 |
| **500** | **339.0ms** | **21.3ms** | **~360ms** | **500** |

Larger packs: higher single-prefetch latency, but 5x more cache population
per round trip. Sequential workloads (filesystem traversal, boot) win from
the prefetch. Random reads use range-read regardless.

## S3 PUT Cost

S3 charges per-operation ($5/million PUTs). Fewer, larger packs = fewer PUTs.

### Flush Model

Flushes are **event-driven**: the write path notifies the flush scheduler
when dirty blocks reach `blocks_per_pack` (configurable per-export, default
500). No periodic S3 flush timer exists — the 5-second checkpoint is local
only (WAL truncation, no S3).

This means:

- Dirty blocks accumulate until the pack-size threshold is crossed
- A VM writing slowly may hold dirty blocks for minutes before triggering
- `drain` and `snapshot` force-flush everything regardless of count
- Exports with `flush_mode = "manual"` never auto-flush; drain-only

### Measured write volume (npm install workloads)

Tool: `block_churn_measure --base base.raw --duration-secs 60 fork*.raw`

These are **total unique blocks changed** during a one-shot `npm install`
on a 512MB forked ext4 image, not sustained rates:

| Workload | Dirty Blocks | Data Volume | Packs at 500 |
|----------|-------------|-------------|--------------|
| Express (1 pkg) | 50 | 6.2MB | 1 |
| Next.js (3 pkgs) | 1,071 | 134MB | 3 |
| App (express + code) | 61 | 7.6MB | 1 |

Most workloads produce **1-3 packs total** per deploy. This makes pack size
nearly irrelevant for deploy-time S3 cost — it's 1-3 PUTs regardless.

### Steady-state cost model

The deploy burst is cheap. Steady-state writes (logging, journald, temp
files, database data files) are what determine ongoing PUT cost.

**We have not measured steady-state write rates yet.** The estimates below
are informed guesses. The `block_churn_measure` tool measures one-shot
diffs, not continuous rates. See [Measurement Gaps](#measurement-gaps).

```
PUTs/month = unique_blocks_dirtied_per_day * 30 / blocks_per_pack
PUT cost   = PUTs / 1,000,000 * $5
```

Estimated sustained unique write rates:

| Workload | Unique blocks/sec | Confidence | Notes |
|----------|------------------|------------|-------|
| Idle VM (systemd, journald) | 1-3 | Low | Logs hit same 128KB regions |
| App server (web service) | 2-10 | Low | Most I/O is network, not disk |
| DB data files (WAL on NVMe) | 5-20 | Low | bgwriter trickle |
| Build / npm install | Burst only | **Measured** | 50-1,071 total blocks, then zero |

Fleet steady-state is dominated by app servers. Using 5 unique blocks/sec
(estimate, 1000 VMs):

| Blocks/Pack | PUTs/VM/day | PUTs/Mo (1K VMs) | PUT Cost/Mo |
|-------------|------------|-------------------|-------------|
| 100 | 4,320 | 130M | $648 |
| 200 | 2,160 | 65M | $324 |
| **500** | **864** | **26M** | **$130** |

These numbers need validation against real production traffic.

### Write coalescing

Same block written N times between flushes = 1 dirty block. Larger packs
take longer to fill, extending the coalescing window. A block dirtied early
has more time to be overwritten before the pack flushes. For hot-set workloads
(databases, logging), the effective unique count per pack can be well below
`blocks_per_pack`, giving fewer PUTs than the formula predicts.

This coalescing effect is the strongest argument for larger pack sizes, but
**we haven't measured it**. Need: overwrite ratio under real workloads.

## Memory

Pack assembly takes ownership of compressed blocks and frees each `Vec<u8>`
as it's copied into the output buffer. Peak memory per pack = compressed
output size (not raw + compressed as in earlier versions).

The flush path uses `buffer_unordered(4)` to pipeline assembly and upload —
at most 4 packs are in-flight simultaneously.

| Blocks/Pack | Per-Pack Peak | Flush Peak (4 in-flight) |
|-------------|--------------|-------------------------|
| 100 | 6.5MB | 26MB |
| 200 | 12.9MB | 52MB |
| **500** | **31.9MB** | **128MB** |
| 1000 | 63.2MB | 253MB |

At 500 blocks/pack: 128MB during flush. Even 1000 at 253MB is manageable.

## Tradeoff Summary

| Factor | Favors smaller packs | Favors larger packs |
|--------|---------------------|---------------------|
| S3 PUT cost | | Fewer PUTs (linear) |
| S3 GET amortization | | Better amortized cost (1/N) |
| Prefetch latency | Lower (37ms at 25) | Higher (360ms at 500) |
| Range-read latency | Irrelevant | Irrelevant |
| Memory | Lower | Higher (but manageable) |
| Flush trigger rate | More frequent, smaller | Less frequent, larger |
| Write coalescing | | Longer window = more overwrites absorbed |
| GC granularity | Less zombie storage | More zombie storage (no compaction) |

## Recommendation

**Default `blocks_per_pack` to 500. Configurable per-export.**

1. **Deploy cost is trivial.** Measured: 1-3 packs per `npm install` fork.
   Pack size barely matters for deploy-time S3 cost.

2. **Steady-state cost is the unknown.** The fleet cost model depends on
   sustained unique write rate, which we haven't measured. At 500 blocks/pack
   the math works if steady-state is <20 unique blocks/sec (estimated range
   for app servers). Need production data to confirm.

3. **128MB flush peak is fine.** 4 packs in-flight at 31.9MB each.

4. **Range-read path makes prefetch latency tolerable.** Single-block access
   uses S3 range requests (~20ms) regardless of pack size.

5. **GC granularity is the real cost — but storage is cheap.** A 500-block
   pack (~32MB) with 1 dead block holds ~32MB hostage. S3 storage is
   $0.023/GB/month — $0.0007/month per zombie pack. Spatial clustering data
   shows blocks written together die together, limiting zombie accumulation.

6. **Manual flush mode for dev workloads.** Exports with `flush_mode = "manual"`
   skip auto-flush entirely — dirty blocks only flush on drain/snapshot/shutdown.
   No S3 PUT cost during active development.

Why not 1000: 253MB flush peak matters on smaller instances. 63MB S3 objects
are slow to upload on constrained networks.

Why configurable: workloads vary. Write-heavy fleets benefit from 500+.
Read-heavy or latency-sensitive deployments may prefer 200.

## Measurement Gaps

### What we've measured

- Pack assembly/prefetch/compression performance at various sizes (`pack_size_measure`)
- One-shot block churn for 8 workload types, forked and independent (`block_churn_measure`)
- Spatial clustering of dirty blocks across all workloads
- Cross-filesystem comparison (ext4/XFS/btrfs — minimal difference)

### What we have but haven't used in production

- **Write trace infrastructure** — `WriteTracer` in the NBD handler records
  every block write with microsecond timestamps. Enable per-export via config.
  Produces binary trace files analyzed by `write_trace_analyze`, which reports:
  - Write rate timeline (sliding windows)
  - Hot set analysis (block write frequency distribution)
  - Overwrite ratio (raw writes / unique dirty blocks)
  - Pack fill simulation with flush timing
  - Burst detection

### What we still need

1. **Sustained write rate under real workloads** — how many unique blocks/sec
   does a running web server, database, or IDE produce over hours? The fleet
   cost model depends on this number. Enable `WriteTracer` on alpha exports
   and run `write_trace_analyze` on the output.

2. **Overwrite ratio** — determines how much coalescing the pack-size window
   actually buys. The trace analyzer computes this; need real trace data.

3. **Dirty block accumulation curve** — linear? bursty? logarithmic (hot set
   saturation)? The trace analyzer's timeline view answers this.

4. **Block lifetime** — once written, how long before overwrite or export
   deletion? Determines GC zombie duration. Requires long-running traces.

5. **Database workloads** — pgbench, sqlite, small-scale postgres. The
   gen_dedup_images.sh script can be extended, but database writes are
   better measured via live traces (WAL writes are temporal, not one-shot).

### Tools

| Tool | What it measures | Input |
|------|-----------------|-------|
| `pack_size_measure` | Compression, assembly, prefetch performance | Raw disk images |
| `block_churn_measure` | One-shot block diff (churn volume, clustering) | Base + fork images |
| `write_trace_analyze` | Temporal write patterns (rate, hot set, coalescing) | Binary trace files |
| `WriteTracer` (handler) | Records per-block writes with timestamps | Enabled per-export |
