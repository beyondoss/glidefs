## Best mechanism PER TYPE (empirically established)
- EROFS (read-only rootfs; bless can reorder via PriorityOrder):
    → BUILD-TIME REORDER. 1 GET, guaranteed 1 RTT regardless of scatter. 60-150ms.
      Best overall. 4.5-30x over readahead on real apps.
- ext4 / raw / layered (writable / streamed / content-addressed — CANNOT reorder layout):
    → RUNTIME PARALLEL PRECISE WARM of the captured boot block list. Fetch EXACTLY the
      boot blocks concurrently (window=0, no over-fetch), at device open. Zero waste;
      ceil(blocks/concurrency) RTT waves. 2-11x over readahead. GET/byte counts are
      concurrency-independent, so at concurrency>=128 it closes to ~near-reorder (~169ms
      for python_full). Recommend a high warm fan-out.
- Tiny single-pack images (busybox): readahead already ~optimal (59ms); reorder/warm marginal.

## CRITICAL negative result
- DO NOT implement the ext4/raw warm as a naive parallel 32MiB-window-coalesced fetch
  ("warm-window"): concurrent reads race before the cache populates and each pull overlapping
  32MiB windows → 872-2261 MiB fetched for a ~10 MiB boot set, 9-23s — ~20x WORSE than
  readahead. The warm MUST fetch the precise block list (or tightly-coalesced exact runs),
  not windows.

## Why mechanisms differ
The win is GET-count (RTTs) + over-fetch (bytes). Reorder makes the set contiguous → 1 GET,
exact bytes — only EROFS can reorder at bless. Non-reorderable images keep the scatter, so the
warm must (a) fetch EXACT blocks to avoid over-fetch, and (b) parallelize to hide the many RTTs.
Readahead fails because it's reactive (serial RTTs) AND window-coalesced (massive over-fetch on
scattered sets).

## KEY per-type insight (NEW): layout locality determines how much readahead already wins
- Monolithic (ext4 / raw / EROFS-before-reorder): boot set scattered across the WHOLE image
  → readahead over-fetches 2-12× (python_full: 387 MiB to serve 31 MiB) → big win for a precise
  fetch / reorder.
- Layered: each layer's boot files are naturally CLUSTERED in that layer's own packs, so the
  boot set is "pre-clustered" per layer → readahead is already decent (4 GETs, 1.2× over-fetch)
  → warm-precise wins only ~1.5×, mostly by cutting bytes (7.2 vs 36.8 MiB). Layering is itself
  a (coarse) locality optimization.

## FINAL best-mechanism-per-type (all empirically proven)
- EROFS    → build-time REORDER (1 GET; 4.5-30×). Reorderable, biggest win.
- ext4     → runtime PARALLEL PRECISE WARM (2-11×). Cannot reorder.
- raw      → runtime PARALLEL PRECISE WARM (1.7× here; scales with scatter). Cannot reorder.
- layered  → runtime PARALLEL PRECISE WARM, ideally COALESCED per-layer-pack (1.5×, mostly
             bytes). Cannot reorder (shared immutable layers); per-layer locality already helps,
             so the warm's job is mainly killing over-fetch. 218 tiny GETs argues for per-layer
             coalescing (each layer's boot blocks sit in 1 pack) over pure per-block precise.
- ALL non-EROFS: never use naive parallel 32MiB-window warm (races → 9-23s).

## NEW INSIGHT — filesystem layout drives how scattered the boot set is (within packs):
- btrfs (copy-on-write, B-trees): SCATTERS the boot set badly within its packs → readahead
  over-fetches ~6.3× (≈196 MiB to serve 31 MiB), the WORST of any type measured → warm-precise
  wins 5.6×, a reorder would win 15×.
- f2fs / "flashfs" (log-structured, flash-optimized): better write locality → readahead
  over-fetches only ~2× → warm-precise wins 1.8×.
Both are NON-reorderable by our bless (only EROFS reorders) ⇒ shippable mechanism = runtime
PARALLEL PRECISE WARM for both. warm-window catastrophic as always (951-1666 MiB).

## Per-type mechanism — COMPLETE (6 fs types proven)
  EROFS  → build-time reorder           (1 GET, 4.5-30×)            [reorderable]
  ext4   → parallel precise warm        (2.2×)                      [not reorderable]
  raw    → parallel precise warm        (1.7×)                      [not reorderable]
  layered→ parallel precise warm/coalesced (1.5×, per-layer local)  [not reorderable]
  btrfs  → parallel precise warm        (5.6×; CoW scatters most)   [not reorderable]
  f2fs   → parallel precise warm        (1.8×; log-structured local)[not reorderable]

## CHURN EXPERIMENT — does locality survive writes? (ext4 vs btrfs vs f2fs, fresh vs churned)
Same rootfs, 1 GB images, identical churn (4 rounds: create 100 files/delete 70% to fragment
free space + atomic-replace cp+mv of ~600 boot files/round = realistic package-update churn),
re-blessed + re-profiled. RTT=40ms, 100 MiB/s, conc=32. over-fetch = readahead bytes / boot bytes.

fs     state   readahead(GET/ms)  over-fetch   warm-precise(ms)   reorder(ms)
ext4   fresh    7 /  678          1.55×         349                125
ext4   churn   10 / 2068 (3.0×↑)  6.4×          354 (flat)         130
btrfs  fresh    9 / 2631          7.3×          410                151
btrfs  churn   10 / 3270 (1.2×↑)  9.0×          412 (flat)         153
f2fs   fresh    6 /  828          2.0×          348                124
f2fs   churn    8 / 2674 (3.2×↑)  7.9×          389 (flat)         124

## CONCLUSIONS
1. f2fs's locality is a WRITE-ONCE artifact. Fresh f2fs (2.0×) ≈ ext4 (1.55×) << btrfs (7.3×),
   but CHURN destroys it: f2fs → 7.9× over-fetch, as bad as btrfs (9.0×). Under churn ALL three
   converge to ~6-9× readahead over-fetch — the filesystem choice WASHES OUT. So "f2fs good for
   a writable/churning position-based blockstore" is FALSE; true only for write-once bases
   (where EROFS+reorder dominates anyway). The log-append + free-space-fragmentation scatters
   the boot set in churn-order, not boot-order; f2fs GC compacts by validity, not affinity, so
   it does not restore boot locality.
2. THE DURABLE LEVER IS THE MECHANISM, NOT THE FS. warm-precise and reorder are CHURN-IMMUNE
   (349→354, 410→412, 348→389 ms; reorder ~constant) because they fetch the EXACT boot blocks
   (byte count fixed regardless of scatter) or re-collocate at bless. readahead degrades up to
   3.2× under churn → the warm's win over readahead GROWS with churn: ext4 1.9×→5.8×,
   f2fs 2.4×→6.9×, btrfs 6.4×→7.9×.
3. DESIGN: for a writable/churning blockstore, do NOT rely on guest-FS layout (it all rots) —
   rely on the precise warm (fragmentation-immune). FS choice matters only for fresh/write-once
   images: prefer f2fs/ext4 over btrfs there; for read-only rootfs, EROFS+reorder wins outright.
