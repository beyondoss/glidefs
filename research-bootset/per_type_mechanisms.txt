=== PER-TYPE mechanism study (RTT=40ms, 100 MiB/s, warm concurrency=32) ===
Candidate mechanisms, all on the REAL image+trace; GETs/bytes EXACT, time = cost model
(readahead serial = GETs*RTT + bytes/tput; warm parallel = ceil(GETs/conc)*RTT + bytes/tput;
reorder = 1 GET).
  readahead    = 32MiB pack-window, reactive/serial        (today's baseline, any type)
  warm-precise = parallel warm of EXACT boot blocks         (ext4/raw/layered delivery)
  warm-window  = parallel warm, 32MiB-coalesced per pack    (ext4/raw ALT — races, over-fetches)
  reorder      = build-time contiguous prefix, 1 GET        (EROFS delivery)

## Best mechanism PER TYPE (empirically established)
- EROFS (read-only rootfs; bless can reorder via PriorityOrder):
    → BUILD-TIME REORDER. 1 GET, guaranteed 1 RTT regardless of scatter. 60-150ms.
      Best overall. 4.5-30x over readahead on real apps.
- ext4 / raw / layered (writable / streamed / content-addressed — CANNOT reorder layout):
    → RUNTIME PARALLEL PRECISE WARM of the captured boot block list. Fetch EXACTLY the
      boot blocks concurrently (window=0, no over-fetch), at device open. Zero waste;
      ceil(blocks/concurrency) RTT waves. 2-11x over readahead. GET/byte counts are
      concurrency-independent, so at concurrency>=128 it closes to ~near-reorder (~169ms
      for python_full). Recommend a high warm fan-out.
- Tiny single-pack images (busybox): readahead already ~optimal (59ms); reorder/warm marginal.

## CRITICAL negative result
- DO NOT implement the ext4/raw warm as a naive parallel 32MiB-window-coalesced fetch
  ("warm-window"): concurrent reads race before the cache populates and each pull overlapping
  32MiB windows → 872-2261 MiB fetched for a ~10 MiB boot set, 9-23s — ~20x WORSE than
  readahead. The warm MUST fetch the precise block list (or tightly-coalesced exact runs),
  not windows.

## Why mechanisms differ
The win is GET-count (RTTs) + over-fetch (bytes). Reorder makes the set contiguous → 1 GET,
exact bytes — only EROFS can reorder at bless. Non-reorderable images keep the scatter, so the
warm must (a) fetch EXACT blocks to avoid over-fetch, and (b) parallelize to hide the many RTTs.
Readahead fails because it's reactive (serial RTTs) AND window-coalesced (massive over-fetch on
scattered sets).
