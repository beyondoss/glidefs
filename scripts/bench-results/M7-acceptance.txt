M7 multiplex ublk transport — acceptance bench
Run: 2026-05-10, host paraglide (16-core, single-NUMA, NVMe)
Daemon: jared/multiplex-ublk @ <commit pending>
Kernel: 6.12.74+deb13+1-amd64

Architecture: worker pool of K=16 threads, each owning one io_uring + executor,
hosting many ublk queues from many devices. Queues distributed by
hash(export_name) XOR qid_seed(qid) mod K. Slab/freelist executor for
churn-safe slot reuse.

==============================================================================
Acceptance criteria from plan: we-do-not-need-dazzling-dewdrop
==============================================================================

1. Per-device IOPS (single fio, 4k randwrite, depth=64, numjobs=4): >= 350k
2. 8-device aggregate IOPS:                                          >= 1.4M
3. At 1000 active exports, threads added by the pool:                <= 32
4. Hot-restart: all 1000 devices recovered to original paths:        <= 5s

4. Hot-restart recovery time
   -------------------------------------------------------------------
   272 ublk devices QUIESCED, kill -9 daemon, systemctl start.

   First "recovering QUIESCED ublk device" log:  T+0.000
   "Recovered 272 QUIESCED ublk device(s)" log:   T+15.412s

   Per-device cost: 56 ms

   AT TARGET DENSITY (1000 devices): extrapolated 55 seconds.

   Target of 5s/1000 not met. Bumping RECOVERY_CONCURRENCY from 16 to 64 had
   no effect — bottleneck is per-AddQueue kernel ioctl + worker UblkQueue::new
   serialization on the worker thread, not async-side parallelism. A future
   optimization could batch register_files_update across many AddQueues
   targeting the same worker.

==============================================================================
Known issues (filed for follow-up)
==============================================================================

- DELETE export at 1000-device density: ~10 min/device (vs 71 ms when daemon
  is stopped). Caused by glidefs's own flush schedulers saturating the SSD
  such that kernel `ublk_ctrl_del_dev`'s internal `wait_event` (likely
  `ublk_wait_tagset_rqs_idle`) sees no progress. See investigation prompt
  for the next engineer.

- 5s/1000 hot-restart target not met. 55s extrapolated. Architecturally
  fine; needs batched AddQueue/register_files for the speedup.
